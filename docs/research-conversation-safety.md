# Move Fred's memory out of the model

Fred's four failures come from one design choice: the conversation's meaning is decided by fragile signals (the last message alone, one free-text guess from a 1.7B model, fixed cosine numbers), and nothing outside the model remembers what has happened. The fix is to keep a small, deterministic conversation state beside the model: the active topic plus a list of "conditions" such as snakebite or head injury that stays in place until the conversation ends. Then every step checks against that state. Concretely, retrieval should always run twice, once on the raw message and once on the recent thread, and merge the two by rank. Question-versus-chat and emergency labels should come from rules, a cheap embedding classifier and the model's label probabilities, not from a generated word. "Call emergency services" should fire only when a specific red flag is present, never just because no card matched. Absolute cosine cut-offs should give way to rank agreement plus a small trained "does this card fit" check, and each card should carry a reviewed "never when" list so the sprain card cannot open after a snakebite. Almost all of this runs in milliseconds on a phone, so the 2.5 s budget is left for one LLM rewrite on the turns where context actually changes the answer. Evaluation should score each conversation by its worst turn, test paraphrases, report paired "fixed k, broke j" counts, and keep a second held-out set untouched by threshold tuning, because a sealed set of tens of conversations can only detect large differences.

## The snakebite follow-up shows why context must be on by default

The sprained-ankle card opened because "its on his ankle and swelling" looks like a complete query and matched a card confidently, so the rewrite step never ran. Gating the rewrite on "raw search is weak" cannot catch this case, because raw search here is confidently wrong. Published benchmarks show how weak the last message alone is: on QReCC, retrieving with only the current query scored **MRR 3.7**, against **24.0 for simply embedding the whole history** and 36.8 for a trained conversational retriever. On TopiOCQA the figures were 2.2, 20.7 and 42.2 ([ContextualRetriever, EMNLP 2025](https://arxiv.org/html/2509.19700v1)). Human-resolved queries beat the best automatic system by 35% in TREC CAsT 2019 ([CAsT overview](https://arxiv.org/abs/2003.13624)). Context should be the default path, not the fallback.

Rewriting also carries its own risk. On QReCC a T5 rewriter (14.7) did worse than plain history concatenation (24.0), because rewrites over-summarise and drop details ([arXiv 2509.19700](https://arxiv.org/html/2509.19700v1)). Researchers found that LLM rewriters sometimes misread the query and hurt retrieval ([InfoCQR](https://arxiv.org/html/2310.09716v2)). Very small models are the weak spot: Llama 1B and 3B "are unable to learn from few-shot examples" for query reformulation ([Lupart et al., SIGIR-AP 2025](https://arxiv.org/pdf/2510.03795)). The lesson for Fred is to **never replace the raw message with a rewrite, but fuse them**. The cheap version needs no LLM at all. Embed the raw message and, separately, the recent turns of the current thread joined to the new message, which is one extra EmbeddingGemma call costing tens of milliseconds. Retrieve with both and merge by rank. In the snakebite case, the thread embedding carries "snake, bit", which should outrank the generic sprain card. When the two lists disagree on the top card, that disagreement is a strong, cheap trigger for the Qwen3 rewrite or for a clarifying question. This applies the idea that disagreement among retrieved results signals an unclear query ([arXiv 2208.04882](https://arxiv.org/pdf/2208.04882)) across two queries.

Retrieval alone should not be trusted to notice a dangerous mismatch. Medical RAG systems that handle contraindications well do it with **explicit, structured contraindication data**. One drug-contraindication system rose from a 0.49–0.57 baseline to 0.87–0.94 accuracy by retrieving structured records rather than reasoning in free text ([arXiv 2508.06145](https://arxiv.org/abs/2508.06145)). Fred's version is simple. It keeps a running conditions list for the conversation, built from keywords and embedding matches against a small vocabulary (snakebite, fall, head or spinal injury, hypothermia, allergy, pregnancy). Each card gets a reviewed `contraindicated_if` field, and before a card is shown the two are compared. A conflict blocks the card and opens the active condition's card, or Fred asks a question. The check takes about 0 ms, can be audited card by card, and addresses the root cause rather than this one bad answer. The same fields can also do document-side work. Following Anthropic's contextual retrieval, which prepends context to each chunk before indexing and cut top-20 retrieval failures by 49% ([Anthropic](https://www.anthropic.com/engineering/contextual-retrieval)), each card's indexed text can say what it is *not* for ("twisted or rolled ankle; not for bites or snakebite"), at no runtime cost. The contraindication lists themselves have to be written from WFA/WFR sources during card review, because no machine-readable wilderness list turned up in the research.

The opposite failure, an old topic taking over, needs the same state. Fred's recent change, which ties a message to the last one only through pronouns that stand in for something already said, fits the literature's finding that not every earlier turn helps and that adding all of them brings noise ([Mo et al.](https://arxiv.org/abs/2306.02553)). Two additions matter. First, "one" in "my friend just got bit by one" is an ellipsis back-reference, so the cue list should include it. Second, history selection should look at the whole session, because topics come back: a later "is he breathing now" should link to CPR even after an unrelated turn. A turn that is far from every earlier turn and has no back-reference is a topic shift, and Fred should use the raw message only for it. The cosine threshold for that call has to be tuned on Fred's own conversations, since no published number carries over to EmbeddingGemma.

## Questions labelled as small talk: stop asking the model to write its label

Asking a 1.7B chat model to generate "WORD | request" is about the weakest way to classify. On a 2026 zero-shot intent benchmark, **Gemma-3-1B scored 0.24 macro F1 and Qwen3-4B 0.40, while the 0.6B Qwen3-Embedding scored 0.56 without any training** ([BTZSC](https://arxiv.org/html/2603.11991)). Few-shot prompts carry well-known biases: toward the label that appears most among the examples, toward the label of the last example, and toward common words. Across prompt formats and example orders, accuracy swings "from near chance to near state-of-the-art" ([Calibrate Before Use](https://arxiv.org/abs/2102.09690)), and the worst example order falls to random-guess level ([Lu et al., ACL 2022](https://aclanthology.org/2022.acl-long.556/)). If CHAT examples dominate or come last, "how much water" turning into "Got it" is the expected result, not a fluke.

Three cheap layers fix this. The first is a **form rule**: a message that starts with a question word or an auxiliary pattern ("how", "what", "should i", "can i", "is it", "do i", "am i") or ends in "?" can never be CHAT. It must not require the "?", because phone and speech input often drops it, and a missing question mark is known to derail dialogue systems ([arXiv 2308.03293](https://arxiv.org/abs/2308.03293)). This rule alone catches all three observed CHAT errors. The second is an **embedding classifier**: Fred already computes an EmbeddingGemma vector for every message, and a logistic-regression head on it adds almost no time. With 8 examples per class, SetFit (355M) reached 71.3% on RAFT against 62.7% for GPT-3 ([SetFit](https://arxiv.org/abs/2209.11055)). A fine-tuned encoder ran in 2.4 ms against about 981 ms for an API LLM and wins "decisively" on stable, labelled domains ([arXiv 2608.20371](https://arxiv.org/html/2608.20371v1)). Fred's five labels are exactly that kind of domain. Embeddings capture topic better than form, which is why the rule layer stays. The third layer uses the **LLM only when the first two are unsure**, and scores it by label probability rather than by generated text. Amazon's cascade, which sends a query to the LLM only when a small classifier is uncertain, came within 2% of LLM accuracy at half the latency ([Arora et al., EMNLP 2024](https://arxiv.org/abs/2410.01627)).

When the LLM is used, Fred should read the probabilities of the five label tokens from one forward pass, with the output restricted to those labels (llama.cpp grammars do this ([constrained decoding](https://www.aidancooper.co.uk/constrained-decoding/))), and then correct for the prompt's bias. Contextual calibration improved accuracy by up to 30 points ([Zhao et al.](https://arxiv.org/abs/2102.09690)). Batch calibration averages label scores over unlabelled real inputs and subtracts that bias at almost no cost ([Google, ICLR 2024](https://arxiv.org/abs/2309.17249)). For Fred, that means one bias vector computed offline per prompt version and stored. Formatting details matter for small models: a leading space before constrained tokens improved accuracy by 5–10% for most models ([Lost in Space](https://arxiv.org/html/2502.14969v1)), so the label words should be checked in Qwen's tokenizer. Low confidence should fall back to QUESTION, meaning the full answer path, because a wrong "Got it" costs far more than an unneeded answer. Qwen3's thinking mode should be off for this call. One gap remains: whether Fred's Android llama.cpp binding exposes top-k log-probabilities still needs checking.

## Emergency must be earned by a red flag, not by a missing card

Every mature triage system works the same way, and it is the reverse of Fred's current logic. Schmitt-Thompson phone triage orders questions from most to least dangerous and lets "the first positive question" set the level ([STCC User's Guide](https://triagelogic.com/wp-content/uploads/2018/12/2018-STCC-OH-Users-Guide_Public-Website-version.pdf)). NHS Pathways, the Manchester Triage System and commercial engines all use 4–6 ordered levels, and even the lowest level includes a specific "if it gets worse" clause ([Infermedica](https://developer.infermedica.com/documentation/engine-api/build-your-solution/triage/); [NHS Pathways](https://digital.nhs.uk/services/nhs-pathways/nhs-pathways-is-a-class-1-medical-device)). No system reaches "emergency" because it couldn't find a protocol. Fred's "labelled NOW, no card matched, so show the emergency reply" assigns urgency with no red flag present.

Over-calling is the documented default of automated triage. In a BMJ audit of 23 symptom checkers, emergencies were triaged correctly 80% of the time but non-urgent cases only 55%, and the advice was "generally risk averse" ([Semigran et al.](https://www.researchgate.net/publication/279990294_Evaluation_of_symptom_checkers_for_self_diagnosis_and_triage_Audit_study)). Safety-focused prompting of LLMs raised safe advice from 89.1% to 94.5% but **raised over-triage from 53.2% to 65.6%** ([J Med Syst 2025](https://link.springer.com/article/10.1007/s10916-025-02284-y)). The published fix is not lower sensitivity but a second stage: a high-recall first pass, then confirmation of a specific red-flag feature ([medRxiv 2026](https://www.medrxiv.org/content/10.64898/2026.01.12.26343914v1.full)). Keyword detectors produce false positives for known reasons: negation, someone else as the subject, hypothetical mentions and past history ([PMC9835770](https://pmc.ncbi.nlm.nih.gov/articles/PMC9835770/)). "Is it safe to touch cholla" is a hypothetical question about a hazard, and "killing me" is hyperbole, not a symptom.

Wilderness curricula provide the red-flag list. They sort cases by evacuation rather than by "emergency or not": no evacuation, go slow, or go fast. "Go fast" is reserved for decreased or changing mental status, worsening vital signs or shock, breathing trouble, spinal-cord signs, and head injury with mental change ([BSA/ECSI WFA Curriculum](https://filestore.scouting.org/filestore/HealthSafety/pdf/680-008(25)-Wilderness-First-Aid-Curriculum.pdf)). Burns need rapid evacuation only when they are large, go all the way around a limb, or involve the airway ([NOLS](https://www.nols.edu/blog/treating-burns-in-the-backcountry/)). A musculoskeletal injury triggers evacuation when it is unusable or unstable ([WMA scope of practice](https://wildmed.com/wp-content/uploads/2013/10/wfa_scope_of_practice_12.pdf)). By these standards, downhill knee pain in someone who can still walk, a small burn blister, and a cholla question carry no evacuation trigger. Professional triage still misses 11–20% of cases ([PubMed 21843217](https://pubmed.ncbi.nlm.nih.gov/21843217/)), so the goal is "no dead end" rather than "never mislabel".

Fred should therefore use three tiers. **Tier 2**, the full "get help now" reply, fires only on an unambiguous red-flag phrase (not breathing, won't wake, bleeding won't stop, snakebite, hot and confused, head hit plus vomiting), and that phrase triggers the reply even with no card match. **Tier 1** is the default for anything health-related: a normal card answer plus a short, specific safety net. The safety-netting literature says good advice names the actual warning signs, gives a time frame and says exactly how to get help, and it discourages vague "come back if worried" advice ([BJGP 2019](https://bjgp.org/content/69/678/e70); [PMC 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC11789814/)). For the knee, that means: "if you can't take weight, it locks, or it swells fast, stop and treat it as an injury." **Tier 0** is plain answers. When no card matches and no red flag is present, Fred should state its uncertainty ("I don't have a reviewed card for that; if anyone is confused, struggling to breathe or bleeding heavily, do X; otherwise tell me more") rather than declare an emergency. "How to get help" also has to fit a place with no signal: SOS or a satellite messenger, moving to high ground, sending a partner. A bare "call emergency services" is the vague kind of advice the literature warns against.

## Fixed cosine numbers punish the follow-ups that most need context

The bear card scored 0.396 on the rewrite but 0.189 on the hiker's own words, so the 0.20 own-words guard rejected it. That is the expected behaviour of absolute cosine scores: a short, vague fragment scores lower against everything than a long, explicit rewrite does. Score normalisation "depends on the score distribution, and that distribution shifts with every query" ([Redis on RRF](https://redis.io/blog/reciprocal-rank-fusion/)). Even CRAG's trained evaluator needed hand-set thresholds for each dataset (0.59 upper on PopQA, 0.95 on Biography) ([CRAG](https://arxiv.org/html/2401.15884)). A single global number cannot be right for both the bear and burn cases.

Rank-based fusion is the standard answer, and it has a track record in exactly this setting. In TREC CAsT, **fusing several query reformulations with reciprocal rank fusion (RRF) cut the gap between automatic and manual rewrites from 22 NDCG@3 points to 4** ([arXiv 2005.02230](https://arxiv.org/pdf/2005.02230)). For Fred, the own-words guard becomes a rank condition: accept the fused top card only if it appears in the top N of both the raw and the thread query lists, with no absolute score required. The 0.29 and 0.15 floors survive only as a coarse out-of-scope filter. A burn card that leads at 0.139 with a clear margin over second place is a hit, not a miss. Per-query margins (top-1 against the median of the top 20) or percentile ranks among all ~12k passages ([Calibrated Fusion](https://arxiv.org/html/2603.28886)) are simple alternatives.

The final "does this card fit this conversation" decision belongs to a small trained scorer, not to cosine and not to a prompted Qwen3. CRAG's fine-tuned 0.77B evaluator judged relevance correctly **84.3% of the time, against 58–65% for prompted ChatGPT**, and its three-way output (correct, ambiguous, incorrect) maps directly onto Fred's answer, ask, or refuse ([CRAG](https://arxiv.org/html/2401.15884)). Small models also "hallucinate or abstain even with sufficient context" ([Sufficient Context](https://arxiv.org/abs/2411.06037)), which supports keeping the refusal decision outside the generator. The realistic phone option is a cross-encoder that reads the query and card together. MiniLM-L6 (22.7M parameters) runs at about 46–58 ms on a desktop CPU ([Superlinked](https://superlinked.com/models/cross-encoder-ms-marco-minilm-l-6-v2)). Qwen3-Reranker-0.6B is stronger (MTEB-R 65.80) and accepts an instruction that defines relevance ([model card](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)), but on a phone it would likely need to be limited to the top five candidates. No phone latency figures were found for either model, so Fred has to measure them. The scorer only helps if its input carries the conversation. Fed the raw fragment, it cannot see the snakebite. Its training data comes from Fred's reviewed cards and sealed-set failures as (conversation, card, fits / doesn't fit / unsafe) triples. That is a small encoder, not the generator, so it stays consistent with the "fine-tuning last" rule. If prompting the LLM as a checker is used at all, it should only be allowed to add refusals, never to approve a card.

## Grade each conversation by its worst turn, and spend the sealed set carefully

Multi-turn unreliability is not specific to small models. When a task is split across turns, performance **drops about 39% on average, and unreliability rises 112%**, for frontier and small models alike ([LLMs Get Lost in Multi-Turn Conversation](https://arxiv.org/pdf/2505.06120)). Medical safety specifically "degrades substantially in multi-turn settings" ([JMedEthicBench](https://arxiv.org/pdf/2601.01627)). Fred's evaluation should therefore measure the worst case. MT-Bench-101 scores each dialogue by its **minimum turn score** ([ACL 2024](https://aclanthology.org/2024.acl-long.401.pdf)). HealthBench uses conversation-specific rubric items worth −10 to +10 points, so a harmful action loses points, and it reports worst-of-k: o3's worst-of-16 score fell by about a third from its roughly 60% average ([HealthBench](https://arxiv.org/html/2505.08775)). Fred's 4-axis, safety-first rubric fits this design. The "unsafe" criteria should become concrete negative items for each conversation, such as "recommends ice or compression after a snakebite", and each sealed conversation should get several paraphrases, reported at worst-of-k.

Statistics limit what a small sealed set can show. With 50 conversations at an 80% pass rate, the 95% confidence interval is about **±11 points**, so two unpaired versions can differ by 15 points without a clear winner. Paired comparison on the same items, counting only the conversations that changed ("fixed k, broke j", or McNemar's test), is far more sensitive ([Adding Error Bars to Evals](https://arxiv.org/abs/2411.00640)). Turns within one conversation are not independent, so either cluster by conversation or count each conversation once through its worst turn. For rare safety failures, zero failures in n items bounds the true rate only below about 3/n: 0/50 means below 6%. Every threshold tuned against the sealed set's failures partly uses the set up, so a **second held-out set that nobody looks at during tuning** is needed before claiming the thresholds generalise.

The blind grader needs its own check. GPT-4-class judges agree with humans about as often as humans agree with each other ([Zheng et al.](https://arxiv.org/abs/2306.05685)), and HealthBench's grader reached macro F1 0.709 against physicians, above physician-to-physician agreement of 0.64 ([HealthBench](https://arxiv.org/html/2505.08775)). But judges flip on 25–50% of position swaps, and raw agreement overstates chance-corrected agreement by 34–41 points ([Reliability without Validity](https://arxiv.org/pdf/2606.19544)). Ryan should grade a random 30–50 items and report Cohen's kappa on the safety axis. A second grader from a different model family, never a Qwen, should flag disagreements for human review. The phone replay harness should feed the same graded pipeline as desktop runs and record timing for each stage, so phone behaviour and the 2.5 s budget are checked on every conversation.

## Prioritised recommendations that fit on the phone

The order below puts safety fixes that cost almost nothing first, and trained components last. Latencies marked "est." are estimates that need phone measurement.

| Priority | Change | Fixes | Phone cost |
|---|---|---|---|
| 1 | Conditions list kept for the whole conversation, plus reviewed `contraindicated_if` on each card; a conflict blocks the card | Snakebite → sprain, shock-card class | ~0 ms |
| 2 | Always retrieve with the raw message and the current-thread embedding; merge by RRF; disagreement triggers the Qwen3 rewrite or a question | Snakebite, stale topic | One extra embed (tens of ms); rewrite 1–3 s only on disagreement |
| 3 | Form rule: a question word, auxiliary pattern or "?" can never be CHAT; requests map to QUESTION; unsure falls back to QUESTION | "How much water", "follow it down" | <1 ms |
| 4 | Three tiers; the full emergency reply only on a positive red-flag phrase; specific safety-net lines on ordinary answers; "no card" never means emergency | Knee, blister, cholla | <1 ms |
| 5 | Replace the own-words 0.20 guard with a rank condition in both lists; keep 0.29/0.15 only as out-of-scope floors; margin rule for emergency cards | Bear, burn | ~0 ms |
| 6 | Evaluation: worst turn per conversation, paraphrase worst-of-k, paired fixed/broke counts, negative safety rubric items, held-out set, kappa check on the grader | Measuring all of the above | Offline |
| 7 | Logistic-regression intent head on EmbeddingGemma vectors (30–100 examples per label); LLM label read from calibrated log-probabilities only when the head is unsure | Remaining label errors | ms; LLM step est. <1 s |
| 8 | Small cross-encoder "fits the conversation" check trained on Fred's triples, with three outcomes: answer, ask, refuse | Residual wrong-card and gate errors | est. <0.5 s for MiniLM over 20 cards |
| 9 | "Not for" lines in each card's indexed text, written at review time | Wrong-card retrieval | 0 ms (re-index) |

## Conclusion

The research changes the question. It is less "how do we make the 1.7B model understand conversations" and more "how little do we need it to". Benchmarks consistently show that small generative models are the least reliable part of the pipeline for classification, relevance judgement and rewriting. Frontier models also lose track across turns. The dependable parts are the ones Fred already has or can add cheaply: embeddings, ranks, rules written by reviewers, and a persistent record of what has been said. Moving safety decisions into that layer makes the worst errors impossible by construction, and it leaves the LLM's 2.5 s budget for the one thing it adds, turning a messy thread into a clean query when the cheap signals disagree.

Two things are still unknown and should be measured before anything is built on them: phone latency for any cross-encoder, and how well EmbeddingGemma separates topic continuation from topic shift on Fred's own conversations. Wilderness contraindication lists also do not exist in machine-readable form. They are review work, and so they belong to the card process Ryan already runs rather than to the code.
